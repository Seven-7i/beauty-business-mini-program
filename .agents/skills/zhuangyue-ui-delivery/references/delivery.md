# 交付流程

## 构建目录一致性

微信开发者工具的项目窗口不会因为命令里传入另一个产物路径就自动切换项目。开始模拟器验证前，先用 `project_list` 读取当前实际导入的 `projectPath`，并让构建命令与该路径一致：

- `app/dist/dev/mp-weixin`：运行 `npm run dev:mp-weixin`，等到首次 `DONE Build complete` 后再执行 `simulator_refresh` 或 `simulator_open_page`。
- `app/dist/build/mp-weixin`：运行 `npm run build:mp-weixin` 后再刷新或打开目标页。

模拟器的尺寸、截图和交互断言必须来自当前 `projectPath` 对应的最新产物。发布构建和 `auto_preview` 仍使用 `app/dist/build/mp-weixin`；不要用 build 目录已更新来推断 dev 模拟器也已更新。

同一 AppID 的 dev/build 目录同时导入时，开发者工具可能复用已打开窗口并继续运行旧产物。构建后先用运行时断言核对一个本轮已修改的明确值；若运行值与磁盘产物不一致，关闭旧目录窗口，对目标目录执行 `debug_clear_cache --action cleanCompileCache`，再打开目标页复测。运行值与磁盘一致后才能截图或 `auto_preview`。

## 开发同步

- 开始实现时列出本轮受影响的需求、交互、UI 图索引和技术说明。每完成一个会改变行为、交互或视觉的实现片段，立即同步对应文档和测试，再继续下一片段；不得把文档集中留到开发结束后补写。
- 文档记录当前实际行为、边界和验证状态，不把关键事实只留在聊天记录、提交信息或代码中。代码与对应文档归入同一逻辑提交批次。
- 所有新增或修改的函数、composable、类型/接口和组件公开契约都使用 JSDoc，写明用途、关键输入输出及边界。可复用代码的 JSDoc 还要列明当前调用页面、组件或模块；调用方变化时同步维护这段说明。
- 注释解释意图、业务约束和复用关系，不复述语法。模板或样式无法使用 JSDoc 时，使用该语言的原生块注释表达同等信息。

## 验证

按风险从紧到宽执行。最终交付必须通过以下命令，除非对应脚本不存在或用户明确缩小验证范围：

```powershell
cd app
npm run type-check
npm run test
npm run build:mp-weixin
```

运行 `git diff --check`。测试因 Windows 沙箱父目录权限失败时，用同一条、最小范围命令申请提升权限后重试，不把权限失败误报成代码失败。

## 真机自动预览

使用微信开发者工具 CLI 的 `auto_preview`，默认参数：

- CLI：`D:\zhangshuang\software\微信web开发者工具\wechatide.cmd`
- client：`codex`
- project：`C:/Users/admin/Desktop/1/r/app/dist/build/mp-weixin`
- page-path：从 `app/src/pages.json` 查找本轮最相关页面；启动流程问题使用 `pages/index/index`

非启动流程找不到目标路由时，视为实现尚未完成，不用 `pages/index/index` 替代目标页预览。

代码通过检查后自动执行真机预览，无需等待用户再次提醒。按以下证据链操作：

1. 记录本轮构建开始时间，并核对目标产物的更新时间晚于构建开始时间。
2. 选择一个能区分本轮代码的明确可观察值或行为，在磁盘产物和模拟器运行时分别核对；动态行为无法直接检索时，用目标页断言或截图证明运行的是本轮产物。
3. 使用该产物执行 `auto_preview`，记录 page-path、完成时间、产物指纹（文件哈希或等价构建标识），并保留工具返回的预览标识或二维码。
4. `auto_preview` 返回 `success: true` 后，只能报告“本轮预览包推送命令成功，待真机确认”，同时给出上述凭据。工具失败或凭据无法对应本轮产物时，报告真实状态，不得声称已经推送。
5. 用户确认手机上已看到第 2 步的本轮变化后，才把状态更新为“真机已更新”。这仍不等于上传体验版或发布正式版。

若手机仍显示旧内容，立即把状态记为“真机未更新”。重新构建并核对产物；必要时清理编译缓存、关闭复用旧目录的开发者工具窗口，并基于同一已核验产物生成新的预览二维码。再次得到用户真机确认前，不得使用“真机已更新”或其他等价表述。

## 分批提交与推送

1. 审查 `git status`、全部 diff 和未跟踪文件，确认没有密钥、生成垃圾或与本轮无关的用户改动。
2. 在执行 `git add` 或 `git commit` 前，向用户列出建议的逻辑批次；每批说明目的、包含路径和建议的 Conventional Commit 信息。避免为了数量机械拆分。
3. 等待用户明确确认可以按该方案提交。讨论方案、要求继续验证或确认真机效果都不视为提交授权。
4. 确认后每批只暂存已告知路径，创建对应提交并复查剩余状态。若文件或批次范围发生变化，先重新告知并等待确认。
5. 已确认的提交完成后，将当前分支普通推送到其远端；用户明确只授权本地提交时不推送。拒绝 force-push、历史重写或删除分支。
6. 最终报告 commit hash、提交范围、推送结果和仍未提交的文件。
