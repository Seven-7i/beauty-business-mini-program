# 微信小程序开发方案

> 文档状态：需求确认后的实施基线  
> 更新时间：2026-07-22  
> 唯一交付平台：微信小程序

## 1. 方案结论

使用 uni-app、Vue 3、TypeScript 和 Vite 开发微信小程序。采用 Composition API 与 `<script setup lang="ts">`，业务数据只使用微信小程序本地 Storage，备份通过用户主动导出未加密 JSON 文件完成。

Android 只是非承诺性的未来可能性，不是当前构建、兼容或验收目标。项目仍将业务规则与微信专有 API 隔离，但不要求组件、依赖或 UI 提前验证 Android。技术取舍见 `docs/adr/0001-use-uni-app-for-wechat-mini-program.md`。

## 2. 技术基线

| 项目 | 选择 |
| --- | --- |
| 框架 | uni-app + Vue 3 + Vite |
| 语言 | TypeScript |
| 组件 | `.vue` SFC，Composition API，`<script setup lang="ts">` |
| 状态 | 最小响应式状态、只读暴露、显式 actions |
| 页面配置 | `pages.json` |
| 本地存储 | `uni.getStorage` / `uni.setStorage` 等 Storage API |
| 构建目标 | `MP-WEIXIN` |
| 测试 | Vitest 单元测试、微信开发者工具、微信真机流程测试 |

开始阶段锁定 Node、uni-app、Vue、Vite、TypeScript 和 HBuilderX/CLI 版本，并提交 lockfile。升级编译器或基础库前在分支完成真机回归。

本期不采用服务端、云数据库、登录、在线支付、推送、媒体上传、Web/H5 套壳或 Android 构建。

## 3. 架构

```text
pages（路由与页面编排）
  ↓ props / typed events
components/features（功能 UI）
  ↓ use cases
composables + stores（页面状态与跨页状态）
  ↓ services（纯业务规则与状态流转）
  ↓ repositories（实体、索引、迁移）
  ↓ storage adapter（uni Storage 与临时文件）
```

| 层 | 职责 | 不应包含 |
| --- | --- | --- |
| 页面 | 路由参数、生命周期、组合功能组件 | 大段业务 UI、库存算法、Storage key |
| 功能组件 | 表单、列表、选择器、确认交互 | 直接写 Storage、跨域业务规则 |
| composable/store | 草稿状态、加载状态、显式动作、跨页共享 | 重复派生数据、任意外部修改入口 |
| service | 校验、库存、金额、状态流转、统计 | 页面实例、具体 Storage API |
| repository | CRUD、索引、迁移、恢复写入顺序 | UI 文案和视觉状态 |
| adapter | 序列化、容量、文件、微信能力封装 | 顾客、项目等领域判断 |

微信专有 API 只能出现在 `infrastructure/wechat/`，页面和业务层通过接口调用。

## 4. Vue 3 实现规则

1. SFC 顺序统一为 `<script setup lang="ts">`、`<template>`、`<style scoped>`。
2. 组件使用 PascalCase 文件名和标签；样式优先使用局部 class。
3. props 只读，变更通过带类型的 emits 或明确的 `v-model` 合约向上提交。
4. 路由页面保持为组合表面；独立表单、列表、筛选、状态操作必须拆分。
5. 表单对象主要使用 `reactive`；会整体替换的集合使用 `ref`；原始值按版本能力使用轻量 ref。不得直接解构 `reactive` 造成响应性丢失。
6. 搜索结果、可用库存、金额、统计和排序使用纯 `computed` 派生，不用 watch 维护副本。
7. watch 只处理副作用，不自动深度监听整个表单写入 Storage。
8. composable 返回只读状态和显式 actions；纯格式化函数放 `utils/`，不伪装成 composable。
9. 列表使用稳定 ID 作为 `:key`，不在同一元素混用 `v-for` 与 `v-if`。
10. 用户输入只通过文本插值展示，不使用 `v-html`。

## 8. 业务服务

### 8.1 `inventory-service`

- 校验单位精度和“名称 + 单位”唯一性。
- 汇总其他待执行预约占用，计算可用库存。
- 校验库存不为负且不低于占用。
- 生成补货、盘点和预约消耗变动。
- 更正已完成预约用量时按差额补回或补扣。

### 8.2 `appointment-service`

- 从多个项目生成快照、标准金额、总时长和合并默认用量。
- 项目组合变化时整体覆盖实际用量。
- 校验至少一个且项目不重复、地址必填、库存足够。
- 检测服务时段重叠，只返回警告而不强制阻止。
- 完成、撤销完成、取消、恢复取消和各状态删除。
- 派生逾期，不把它持久化为状态。

### 8.3 `customer-service`

- 校验唯一昵称、中国大陆 11 位手机号和地址结构。
- 处理停用、重新启用和引用保护。
- 汇总顾客完成次数与成交金额。

### 8.4 `statistics-service`

- 按实际完成时间统计本月完成数和成交金额。
- 待执行数量、首页近期预约和顾客累计数据均从源记录派生。
- 不保存可重新计算的统计副本。

## 9. 本地存储设计

微信小程序 Storage 单个 key 约 1MB、总量约 10MB。目标数据总量控制在 7MB，为索引更新、迁移和临时操作保留空间。

原则：

1. 实体记录使用独立 key，轻量索引按固定大小分片，任何 key 不接近 1MB。
2. 不把全部实体放入单个 JSON。
3. 避开 `uni-`、`uni_`、`dcloud-`、`dcloud_` 保留前缀。
4. 每次写入前后读取容量信息；达到 7MB 显示导出和清理提示。
5. 不自动删除或压缩掉业务信息。

```text
bm:meta:schema
bm:settings
bm:modules:unlocked
bm:backup:metadata
bm:index:{entity}:{chunk}
bm:inventory:{id}
bm:movement:{id}
bm:project:{id}
bm:customer:{id}
bm:customer:nickname:{normalizedNickname}
bm:customer:phone:{phone}
bm:appointment:{id}
bm:txn:recovery
```

Storage 不提供跨 key 事务。多记录操作使用事务意图标记、固定写入顺序和启动恢复：

1. 写入操作意图与旧值引用。
2. 写实体记录。
3. 更新分片索引和唯一索引。
4. 校验结果后清除意图。
5. 启动发现未完成意图时回滚或重放，并向用户报告。

完成预约和更正用量必须将库存变动与预约状态视为同一业务事务。不得仅扣库存但保留待执行状态。

## 10. 备份与恢复

```text
format: "zhuangyue-local-backup"
formatVersion
createdAt
appVersion
payloadChecksum
scope:
  kind: "system" | "modules"
  moduleIds?: ["beauty", ...]
data: 完整应用数据 | 按模块标识组织的模块数据
```

旧 `beauty-local-backup` 文件继续按完整系统范围读取。每个业务模块注册自己的提取、校验和替换处理器；系统级选择模块备份与模块内数据页调用同一处理器。

`payloadChecksum` 只检测损坏，不提供保密或防篡改。导出文件包含顾客资料，界面必须提示未加密风险。

微信文件生成、转发和文件选择封装在 `infrastructure/wechat/backup-file-adapter.ts`。最近时间字段统一为 `lastExportedAt`，界面显示“最近导出时间”。

恢复流程：

1. 在不修改当前 Storage 的情况下解析并完整校验文件。
2. 检查格式版本；旧版运行迁移，未来版提示升级。
3. 恢复确认显示完整系统或具体模块范围；已有范围内数据时提供同范围的先导出入口和覆盖确认。
4. 保存恢复事务标记和可回滚的当前数据快照；阶段 0 必须真机验证回滚文件方案不会受 10MB Storage 限制。
5. 完整系统按固定顺序整体写入；选择模块在共享 FIFO 内基于最新快照只替换所选模块，重建相关索引并校验。
6. 成功后清除恢复标记和临时快照；失败时回滚当前数据。

七天提醒使用 `firstBusinessDataAt`、`lastExportedAt` 和 `lastReminderDate`：到期后同一自然日最多显示一次，“稍后”只更新当天已提醒标记，不改变导出基准。

## 11. 错误与边界

- Storage 写入失败：保留表单，提示检查空间并提供导出入口。
- 读取或迁移失败：进入只读保护，不自动清空。
- 唯一性冲突：阻止保存，并提供查看已有对象入口。
- 库存不足：逐项显示最大可用量或缺少量。
- 快速新增失败：回到原表单，原草稿不丢失。
- 备份生成、分享取消或失败：不更新最近导出时间。
- 恢复校验或写入失败：保留恢复前数据。
- 已停用对象：历史可见，新业务选择器默认隐藏。

2. 新增库存物品、补货、盘点、编辑手工记录和引用保护。
3. 创建多项目预约，验证用量合并与项目变化覆盖。
4. 快速新增顾客、项目和库存物品后草稿不丢失。
5. 多地址选择、临时地址和地址快照。
6. 完成、更正、撤销完成、取消、恢复和删除的库存联动。
7. 月历、逾期、时间冲突和首页提醒。
8. 未加密导出、微信手动转发、取消不更新时间。
9. 有效、旧版、未来版和损坏备份恢复。
10. 恢复中断后原数据可恢复。

### 12.3 容量与性能测试

生成 200 位顾客、50 个项目、200 种库存物品、2,000 条预约和 8,000 条库存变动的真实结构数据：

- Storage 总占用目标不超过 7MB。
- 任一 key 不超过 1MB。
- 常用列表首次显示目标不超过 1 秒。
- 本地搜索反馈目标不超过 300 毫秒。
- 容量到 7MB 时提醒，不自动删除。
- 备份、恢复和迁移在接近目标容量时仍可完成或安全失败。

## 14. 开发准入与完成标准

开始业务代码前必须完成阶段 0，尤其是微信文件流程、接近容量时的恢复回滚和分片索引验证。

每个功能完成时必须满足：

- 规则与 `docs/微信小程序需求文档.md`、`CONTEXT.md` 一致。
- 路由页面保持薄，组件 props/emits 和 composable API 有类型。
- 业务计算有单元测试，关键状态操作有回归测试。
- 失败不清空表单、不静默丢数据、不产生部分库存扣减。
- 不新增媒体、服务端、登录、支付、推送或 Android 兼容范围。
