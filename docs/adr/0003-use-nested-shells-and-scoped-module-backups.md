# 使用全局与模块两级导航，并让备份显式声明范围

## 背景

应用将支持多个相互独立的业务模块。日程、报表和业务数据保护都属于具体模块，把美容日程与美容报表放进全局底部导航，会让增加第二个模块后的页面归属变得含糊。另一方面，用户既需要完整迁移整个应用，也需要只导出或恢复某个模块；恢复某个模块时不能覆盖其他模块、个人设置或授权状态。

## 决策

应用采用两级导航壳：全局壳只提供“工作台”和“我的”，模块壳拥有当前模块自己的首页、日程、报表和数据页签。两级页签状态分别由各自组合根管理，模块组件不修改全局页签。

备份文件必须声明以下一种范围：

- 完整系统：包含个人设置、模块授权状态和所有模块数据；
- 选择模块：只包含明确列出的一个或多个模块数据。

每个业务模块通过自己的备份处理器提取、校验和汇总模块数据。系统级备份编排调用相同处理器组合用户选择的模块，模块内数据页也调用该处理器，但固定为当前模块。完整恢复继续使用整体快照替换；选择模块恢复必须在应用数据仓储的共享写入队列内，基于提交时的最新快照只替换所选模块，并沿用事务回滚保护。

旧版完整备份仍按完整系统范围兼容读取。备份预检先验证格式、校验和、范围及模块数据，再允许任何写入。

## 不采用的方案

- 不把所有模块的日程和报表继续放在全局导航：页面归属会随模块增加而冲突。
- 不为系统级和模块内备份各写一套导出逻辑：两套校验和格式容易漂移。
- 不把模块恢复实现为页面先读完整快照、合并后再整体写回：读写窗口会静默覆盖期间发生的其他模块或全局变更。
- 不把选择模块恢复定义为逐条合并：重复标识、删除事实和引用关系会产生不可预测结果。

## 结果

全局入口保持稳定，新增模块可以拥有独立的内部信息架构。备份界面必须清楚显示文件范围和将被覆盖的模块；模块备份成功不能更新“完整系统备份”的七天提醒基准。新增业务模块时，需要同时注册它的导航入口和备份处理器，并为选择恢复的隔离性、并发写入和失败回滚增加测试。
