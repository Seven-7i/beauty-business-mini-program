# 日常业务写入使用命令式原子变更接口

## 背景

应用数据仓储已经支持完整快照读取、备份恢复和中断回滚。阶段 2 开始后，新增库存物品、补货、盘点修正和保存服务项目属于高频日常写入，不能让页面理解 Storage key、分片索引、写入意图或回滚顺序，也不能直接调用面向整体恢复的 `replaceSnapshot()`。

一次业务操作可能同时改变多个事实。例如补货必须同时更新库存物品当前库存并新增库存变动记录；任一步失败都不能只留下其中一半。

## 决策

在 repository 层建立一个命令式业务变更 seam。它的 interface 接收封闭的业务命令联合类型，例如：

- 保存一个库存物品；
- 原子提交“更新后的库存物品 + 新库存变动记录”；
- 保存一个服务项目；
- 按引用规则停用或删除库存物品、服务项目；
- 保存仍处于待执行状态的预约，并按队列内最新数据复核库存占用；
- 原子提交预约完成、更正或撤销完成所涉及的预约、物品库存与预约消耗记录。

每个命令只携带已经通过 service 业务校验的领域对象和必要意图，不暴露 Storage key、索引位置或事务步骤。repository 实现负责：

1. 进入全局共享 FIFO 写入队列；
2. 先恢复任何未完成事务；
3. 复核命令涉及的实体标识和引用前提；
4. 写入操作意图并保存旧值引用；
5. 更新实体记录、分片索引和必要的唯一索引；
6. 首次产生业务数据时设置 `firstBusinessDataAt`；
7. 读回校验后提交并清理意图；
8. 失败时恢复本次操作前的相关实体和索引。

测试通过同一命令 interface 使用内存 Storage 和内存回滚文件 adapter，故障注入覆盖每个写入窗口。feature 和 page 只能调用该 interface，不得绕过它写入业务 key。

## 不采用的方案

- 不让页面或 composable 直接操作 Storage：这会把事务顺序、索引维护和恢复知识散落到多个调用方。
- 不为每次日常 CRUD 调用完整恢复接口：整体替换会清理并重写全部业务数据，接口语义错误，高频操作成本也会随数据量增长。
- 不暴露通用 `mutateSnapshot(callback)`：回调可以任意改动授权、设置和无关实体，interface 过宽，无法按命令建立局部不变量和故障测试。
- 不把“保存物品”和“保存库存变动”拆成两个公开方法：调用方可能只完成一半，无法保证业务原子性。

## 结果

业务写入模块对调用方保持较小 interface，同时在实现内部集中事务、索引、引用保护和回滚复杂度。新增命令需要同步增加仓储实现、故障注入测试和恢复验证；在该 seam 完成前，阶段 2 页面不得提供会写入真实数据的伪 CRUD。

阶段 3 的预约状态流转继续遵守同一边界。取消预约只释放由待执行预约派生的占用，不生成库存变动；完成预约必须在一个命令内扣减所有涉及物品并生成对应预约消耗；更正和撤销完成必须同步重放库存链。删除已完成预约不能补回库存，只把保留的预约消耗标记为“来源预约已删除”。这些动作在对应命令及故障测试完成前不得先接页面按钮。
